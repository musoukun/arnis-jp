# 写真1枚から Minecraft の建物を作る

- **入力**: 写真1枚（ストリートビューのスクショ等）＋ arnis が保存した OSM データ。他の画像生成 AI は使わない
- **ゴール**: 写真の建物が「だいたい近い」見た目で建つこと。細部の完全一致は狙わない
- **正解例**: ガスト 堺北花田（ユーザー評価「かなりクオリティが高くて感動した」。仕様は下の「6. 正解例」）
- **サンプル**: KFC 堺北花田。設計 `tools/remodel/designs/kfc_kitahanada.py`、お手本と部位の拡大 `examples/kfc_kitahanada/`。
  新しい建物はこの設計ファイルをひな形にする（部位の辞書の部品・入口・自動扉・看板の向き・断面 `sections` が全部入っている）

- **分からない所は、決めつけずに聞く**（下の「0. 聞いてから作る」）

## 0. 聞いてから作る（最優先の決まり）

写真やお手本から**読み取れない・確信が持てない所は、推測で埋めずにユーザーに聞く**。
推測で建てると、壊して建て直す手間がかかり、同じ質問を後で何度もすることになる（KFC で通路・扉・看板の位置を推測で決めて、全部やり直した）。

| いつ聞くか | 例 |
|---|---|
| 写真に写っていない・隠れている | 人や看板の陰、裏の面、屋上の奥 |
| 2通り以上に読める | 「段は飾りか通路か」「看板はどの面を向くか」「扉はどこか」 |
| 部位表の欄が埋まらない | 大きさ・位置・向き・形（フル／ハーフ／塀／柵）のどれかが決められない |
| お手本と写真が食い違う | お手本の作りと実物の写真で、位置や数が違う |
| 道具で作れない形が要る | 部品の不足（作り方を変えてよいか、道具を足すか） |

聞き方:
- **位置・大きさ・色を聞く時は、チャットの中に出す操作できるフォームで答えてもらう**（`mcp__visualize__show_widget`。先に `read_me` を読む）。
  正面の絵（立面）と上から見た絵（平面）をブロックのマス目で描き、**スライダーで位置や幅を動かすとその場で絵が変わる**ようにする。
  **ブロックを聞く時は、色ではなくブロックの見本（実物のテクスチャ）を見せる。** 見本はブロックの一覧表と同じ仕組みから出す
  （`python block_catalog.py samples <ブロック名>...` が data URI を返す。ハーフは下半分だけの絵になる）。絵の中の部位も見本のテクスチャで描き、
  選んだブロックが絵に反映されるようにする。最後のボタンで `sendPrompt("…の答え: …")` を呼び、答えがそのままチャットに入るようにする（ファイルやリンクを開かせない）。
  この表示が使えない環境だけ、Web ページ（Artifact、答えは `db` に保存）で代わりにする
- **別々の部位は、別々に指定できるようにする。** 1本のスライダーで2つの物を同時に動かさない（KFC で左右の通路を1本のスライダーで
  一緒に動かして、個別に決められなかった）。左右の通路のように同じ種類の物が複数あるなら、絵の上で**それぞれをクリックして置く**か、1つずつに操作を付ける
- **ゲームの座標（x・z の数字）を質問に出さない。** 相手に分かるのは「北の角から何マス」「正面の真ん中から南へ何マス」「左右」「手前・奥」
- 絵には目の位置と向き、北と南（左右）、正面の真ん中の目印、人の目印（高さ2マス）を入れる
- 短い確認だけなら、自分の理解を AA（平面か立面の文字の図）で描いて見せ、「ここで合っていますか」と聞いてよい（描き方は 1.5 の「AA で質問」）。
  上から見た図と正面から見た図を1つの絵に混ぜない
- 1回にまとめて聞く（分からない所を全部書き出してから。1つずつ小出しにしない）
- 選択肢があるなら並べて、おすすめを1つ示す（`AskUserQuestion` を使える時は使う）
- **答えをもらうまで、その部位は作らない**（ほかの決まっている部位は進めてよい）
- 答えは部位表と設計ファイルの説明に書き残す（次に同じことを聞かない）

## 1. 変換の法則（このスキルの本体）

正解例と、上手な Minecraft の再現作品（高層マンション・百貨店）の分析から導いた。

### 法則1: 大きさ — 目で見た比率と、人の体で決める（画素を測って換算しない）
**1.4 はワールドの縮尺で、ユーザーの「黄金比」**。ユーザーが自分の目で見た世界とゲームの中の自分の体との比率から決めた数で、
`arnis --scale 1.4` でワールドを生成した時点で、道路・敷地・建物の平面・高架にもう入っている。
**部位（看板・塔・柵・文字・植え込み…）に 1.4 を機械的に掛けない。** 掛けると二重に大きくなる。

| 決めること | 決め方 |
|---|---|
| 平面（幅・奥行き・形） | **OSM のポリゴンをそのまま**（ワールドの縮尺で既に広がっている） |
| 1階の高さ（地面〜帯） | 店舗はおよそ **5 マス**（正解例ガストの柱5）。ここを建物全体の基準にする |
| それ以外の部位の大きさ | **写真を目で見て、基準との比率で決める**（「塔は1階より少し低い」「看板は入口と同じくらいの幅」「屋上の柵は1階の半分くらい」） |
| 人との比べ | プレイヤーは高さ **1.8 マス**。看板・文字・塔・柵を、**その前に人が立った時に大きすぎないか**で確かめる（実物の看板は人の背丈かそれより少し大きい程度） |
| 細いもの | どんなに細くても最低1マス（薄い物はハーフや柵・板で） |

**やらないこと**: 写真にマス目を引いて画素を数える／画素を m に直す／m に 1.4 を掛ける／「低めに出るから大きく」と上乗せする。
この換算を重ねると、どれも大きくする側に振れて、看板や塔が人の何倍もの大きさになった（KFC の失敗）。
人が一目で分かる比率を、そのまま目で見て決める。マス目は、比率がどうしても決められない時だけ使う。

### 法則2: 大きいものから合わせる（大きさで扱いを変える）
| 実物の大きさ | 例 | 扱い |
|---|---|---|
| 5m 以上 | 輪郭、段差、塔と基壇 | 比率を正確に（OSM＋高さの法則） |
| 1.5〜5m | 階、柱間、ひさし、帯 | **数**を合わせる（何段、何マスおき） |
| 0.5〜1.5m | 窓の格子、ルーバー、細い窓 | **密度と凹凸**を合わせる（数はおおよそ） |
| 0.5m 未満 | 手すり、目地、窓枠の細部 | 捨てるか、帯・面に吸収 |
| 文字・ロゴ | 店名、看板 | 法則6 |

### 法則3: 壁は「段の積み重ね」で書く
写真の壁を、下から何の段が何段あるかに分解する（`STACK`）。段の種類は `parts.py` の
`glass`（窓。柱つき・奥に引っ込める）/ `solid`（無地）/ `frame`（上枠）/ `frame+awning`（上枠＋ひさし）/
`frame+balcony`（上枠＋張り出し）/ `band`（帯）。
| 建物の型 | STACK の目安 | 根拠 |
|---|---|---|
| 平屋の店舗（ファミレス等） | `glass×3, frame+awning, band`（柱5マス） | 正解例 |
| 平屋の店舗・ひさし無し（コンビニ等） | `glass×3, frame, band` | 正解例から類推 |
| 住宅・マンションの1階分（4マス） | `glass×3, frame+balcony` を階数だけ繰り返す | 作例分析（**要検証**） |
| オフィス・商業の1階分（5マス） | `glass×4, frame` を階数だけ | 作例分析（**要検証**） |
階数は写真で数えて**数を合わせる**（法則2）。1階分のマス数は丸めてよい。

### 法則4: 屋根
| 写真の屋根 | ROOF | 作り方 |
|---|---|---|
| 寄棟（四方に傾く） | `{"type": "hip", "rise": r}` | 軒先は壁の1マス外。ハーフで 1:2 に上がる |
| 切妻（二方向） | `{"type": "gable", "rise": r, "ridge": "x"または"z"}` | 棟の向きを写真で決める |
| 陸屋根（平ら） | `{"type": "flat"}` | 1マスの手すり壁 |
`r` は基本 2.5（頂部 = 柱 + 3）。写真で明らかに急な屋根なら増やす（0.5 刻み）。屋根は暗い色の方が引き締まる。

**屋上の柵・ルーバー**（陸屋根の店に多い）は [部位の辞書](recipes.md) の「屋上の柵」に従う（KFC は `nether_brick_fence` を3段、向こうが透ける）。
- 段数は、写真を目で見て1階の高さとの比で決める（屋上の物は低い。帯の上に5段も積まない）
- 帯の陰で下の段が隠れないか、横からの絵で確かめる

### 法則5: 奥行きで影を作る（最低3つの面）
張り出し（ひさし・ベランダ・軒 = +1）／壁の面（0）／引っ込み（窓のガラス = −1）。
平らな壁に色を塗るだけだと模型に見える。窓は `glass` の段が自動で1マス引っ込める。

### 法則6: 色は「素材の種類」で選び、差し色は全部残す
**まず [部位ごとの作り方の辞書](recipes.md) を読む。** 色と種類だけで決めると全部フルブロックの塊になる。
部位ごとに、ブロックの形（フル／ハーフ上下／階段／柵／板ガラス）・厚さ・重ね方・置き方を辞書から決める
（植え込みの縁はハーフを積む、軒の下に軒天と吊りランタン、屋上の格子は透ける柵＋支柱、看板の枠と立体文字は1マス飛び出す…）。
| 現実の素材 | ブロック（`parts.DEFAULT_PAL`） |
|---|---|
| コンクリート（舗装・柱・電柱） | `stone_bricks` / 柱は `stone_brick_wall` |
| 黄色い点字ブロック | 木の板（`bamboo_planks`） |
| 店先の赤茶のタイル | `polished_granite` |
| レンガ | `bricks` |
| 生け垣 | `oak_leaves[persistent=true]` |
| 布のひさし | 色付きウールの縞（例 `red_wool`/`white_wool`） |
| ガラス窓 | `gray_stained_glass` |
| 窓枠・暗い柱 | `polished_blackstone` |
| 白い外壁・パネル | `smooth_quartz` / `white_concrete` |
| ブランドの色 | その色のコンクリート（`red_concrete` 等） |
| 瓦・暗い屋根 | `deepslate_tile_slab` |
| 金属のラック・柵 | `iron_bars` |
| 黒いレンガ調の外壁・塔 | `polished_blackstone_bricks` / `deepslate_bricks` |
| 木の枠・木のルーバー | `spruce_planks` / `spruce_trapdoor` |
- **色は対応表で選ぶ**（`block_catalog.py`）。全ブロック（1.21.11 の 1162 個）の「テクスチャ・平均色・一番多く使われている色の範囲とその割合」の表。
  一覧は `python block_catalog.py build` で `out/block_catalog.html`（色相順、名前で絞り込み）
- 手順: ① 写真の範囲を決める → ② **素材の種類を意味で決める**（レンガ・コンクリート・木…）→
  ③ `python block_catalog.py match <写真> x0 y0 x1 y1 6 <種類>`（例 `bricks`）で、その種類の中で色の近い順に
  **実物のテクスチャと写真を並べた絵**（`out/match_*.png`）を作る → ④ 絵を見て模様も近いものを選ぶ
- 種類で絞らないと、色だけ近い別物が上に来る（KFC の黒レンガ → 絞らないと `gray_concrete_powder`、`bricks` で絞ると `deepslate_bricks`）
- 写真は曇りや日陰で色が暗く・くすんで写る（KFC の赤い帯 → `pink_terracotta`、日陰のレンガ → `gray_terracotta` と出た）。
  差し色・ブランドの色は表の答えより**鮮やかな方**（`red_concrete` 等）を選ぶ
- 差し色（帯・ひさし・看板・旗）は**位置と大きさごと全部**残す。白い建物ほど差し色がその建物らしさを決める
- 帯が実物より太くなる（0.4m → 1マス）ので、赤が多く見えたら帯を壁の線（軒の影の中）だけにして、屋根の量で比率を戻す

### 法則7: 文字・ロゴは地図アートで実物大
- 店の顔になる看板（店名・ロゴ）は**地図アート**（額縁に入れた地図。1マスに 128×128 ドット）で実物大に置く
- 看板の裏には**色の近いブロック**（`SIGN_BACKING`）を置く。額縁が見えなくても看板の色の塊に見える
- それ以外の小さな看板は、色の塊（ブロック）だけでよい。文字が読めなくてもかまわない
- 額縁の下や横に支えが無いと浮いて見える。根元まで埋める

### 法則8: 周りまで作る（写っているものだけ）
| 写真の物 | 部品（`parts.py`） | 大きさ |
|---|---|---|
| レンガの植え込み＋生け垣 | `planter` | 縁1マス、生け垣は2段まで |
| 街路樹・小さな木 | `small_tree` | 3マス。窓の前には植えない |
| のぼり旗 | `nobori` | 柵の柱＋模様付きの旗（約3マス） |
| 駐輪ラック | `bike_racks` | 1マス |
| 電柱・看板の柱 | `pole` | 電柱 12マス |
| 店先のタイル・点字ブロック | `ground` | 地面の張り替え |
**窓とひさしを隠さない**: 生け垣は2段まで、木の葉は窓の無い所に。

### 法則9: 入口は必ず「入れる」ようにする
プレイヤーは高さ 1.8、ジャンプで上がれるのは約 1.25。見た目より先に通れることを守る。
| 入口の型 | 作り方 |
|---|---|
| 段差なし（店舗の基本） | 外の地面と室内の床を同じ高さに。開口は高さ3（住宅は2）×幅2以上 |
| ハーフの段（0.5） | 入口前にハーフブロック、室内の床もハーフで同じ高さに（ジャンプ不要） |
| 階段で1段上がる（レンガの土台の上に建つ店など） | 設計に `PLINTH = 1`。土台がレンガになり床が1段上がる。`entrance` が外に階段を置く |
| 扉の前だけフルブロック（よく使う作り） | 扉の前の1マスだけフルブロック、その手前はハーフ。`entrance(..., steps="landing")`。[辞書](recipes.md)の「扉の前の踏み台」 |
- `parts.entrance(c, 壁のセル, 外の向き, height=3)` を `extras` の**最後**に呼ぶ（壁・窓・植え込み・像などを上書きして通り道を空ける）
- 入口の前後2マスに、像・看板・ラック・植え込みを置かない
- 写真で入口に階段があり、建物の足元にレンガ・石の帯が見えたら**土台（`PLINTH = 1`）**。床・壁・窓はすべて土台の上から始まる
- 失敗例: KFC で外に階段ブロックを置き、室内の床は地面のまま・開口2マス → 頭が上枠に当たって入れなかった。
  レンガを「店先の縁」として置き、土台の上に床が乗っていなかった

**入口のデザイン**（正解例の分析から。入口は「ひと目で入口と分かる」ことが大事）:
- 入口は**柱に挟まれた凹み**。両脇に壁の線で2マスずつの柱（帯の下まで）、その1マス奥にガラスの扉、まわりは木の枠
- 扉は床から3マスのガラスに見せる（動く2段 ＋ 上の明かり取り）。奥の室内の明かりが見える
- **入口の階段と床は木**（`PAL` の `step`/`porch_floor` を `spruce_stairs`/`spruce_planks`）。レンガの縁はそこで切る
- **入口の前と左右3マスに看板・柱を立てない**（案内看板は窓の前へ）
- 失敗例: 仕掛けを隠す木の板で壁の線を8マス覆った → 入口が木の壁に見え、窓も消えた。看板が入口の真ん前に立っていた
- 確認は**入口の正面から描いた絵**で（写真の斜めの視点だけでは入口の違いに気づかない）

**自動扉を基本で付ける**（店舗はガラスの自動扉）: `entrance` の直後に
`used = parts.auto_door(c, 入口の壁セル2つ, 外の向き)` を呼ぶ。
- 柱に挟まれた凹みの奥に、木の枠（`door_frame`）で囲ったガラスの扉（幅2・高さ2＋明かり取り）。外と室内の感圧板で開き、離れると閉まる。ピストンは両脇の柱の裏に隠れる
- 仕組み: 粘着ピストン4本が左右からガラスを押し出して閉じている（床のレッドストーントーチで常時通電）。
  感圧板 → 床下の粉 → トーチの台に通電 → トーチが消える → ピストンが縮んでガラスを壁に引き込む
- 配線は床下（床 − 1）に通すので **`PLINTH = 1` 以上が必要**（0 だと扉を付けずに開口のままになる）
- 入口の壁セルは**ちょうど2つ**。左右に4マスずつ仕掛けの幅が要る（壁の端・塔に掛からない位置を選ぶ。両脇2マスは柱になる）
- ピストンは置いた瞬間の通電で伸びるので、`build` の最後に順番どおり置く（`Blocks.ordered`、`run.py` が自動でやる）
- 施工後に**防具立てで試す**: 感圧板の上に `summon armor_stand` → ガラスが消える → `kill` → 戻る、を `execute if block` で確かめる

### 法則10: 正面から見える室内を作る（窓の奥が空っぽだと模型に見える）
`parts.furnish(c, 窓の面, avoid=used)`（`used` は `auto_door` の戻り値）。
| 物 | ブロック | 置き方 |
|---|---|---|
| 机 | 柵1本（`spruce_fence`）＋ 感圧板 | 窓の面の壁から 3 マス内側、4 マスおき |
| 椅子 | 階段（`spruce_stairs`） | 机の前後（壁から 2・4 マス）。背もたれは机の反対側 |
| 明かり | 鎖（`iron_chain`）で吊ったランタン | 天井から、窓の高さ（床 + 3）まで下げて外から光が見えるように |

## 1.5 ミスを防ぐ決まり（KFC の失敗から。必ず守る）

KFC でお手本と比べて10か所違った。原因は10で、どれも「お手本を目で見る前に、別の物で決めていた」こと:
| 原因 | 起きたこと | 決まり |
|---|---|---|
| **道具の都合を形より優先** | ランタンを吊るために帯をフルブロックにした／地図アートが西向きしか置けないので看板を正面に置いた | 部品で作れない形は、形を変えずに**道具の側を直す**（部品の不足として先に報告） |
| **画素を測って換算を重ねた** | マス目で画素を数え → m に直し → ×1.4 → 最低マス数、と重ねて、看板・塔が人の何倍もの大きさになった | **画素を測らない。目で見た比率と人の体で決める**（法則1）。1.4 はワールドの縮尺（ユーザーの黄金比）で、部位に掛けない |
| **数をお手本で数えず、文章のルールや古い座標から決めた** | 塔を高さ8・屋上の柵を5段にした（お手本は塔4・柵3段）／看板と植え込みを古い設計の座標のまま使った | 部位ごとの数（幅・高さ・奥行き・段数・位置・向き）は**お手本を見て部位表に書く**。**古い設計の座標を使い回さない** |
| **指摘された所だけ直した** | 植え込みのハーフを直したのに、同じ「厚さを見る」原則を帯に当てなかった | 指摘を受けたら、その原則で**全部の部位を点検し直す** |
| **形だけ見て、人の動き（動線）を読まなかった** | 植え込みの切れ目と階段を「縁の飾りの段々」と読み、左右2つの通路から衝立の裏を通って扉へ入る作りを見落とした | 部位を見る前に、**歩道から扉まで人がどう歩くか**（車ならドライブスルーの通路）を平面の AA に描く。**段・階段・植え込みの切れ目は通路の印**。「なぜここに段があるのか」を必ず考える |
| **通路の高さを歩く順に考えなかった** | 衝立の裏の通り道を平らな地面のままにし、段は扉の前だけにした（実物は通り道をハーフで底上げし、通路の入口で1段上がる） | 入口・通路は、**横から見た高さの図（断面の AA）を描く**。歩道→通路→通り道→扉の各マスの床の高さをハーフ単位で書き、段をどこに置くかを決めてから作る |
| **軒を形の外周に機械的に回した** | 帯（軒）が壁の1マス外で止まり、前に出た衝立の上を覆わなかった | 衝立・看板・ひさしなど**前に出る物を足したら、上から見た図で軒の線と重ねる**。入口のまわりは軒を前に出して覆う（覆わない時は理由を書く） |
| **辞書に書いた作りが建った物に入っているか確かめなかった** | 辞書は「車止め＝黒い塀の上にランタン」なのに、部品が塀だけを置いていて明かりが付かなかった | 部位表で**ブロックか飾りか**を分ける。ランタン・トーチ・鎖・感圧板・旗などの飾りは、**ブロックを全部置いた後に最後に取り付け**（`Blocks.decor`、`run.py` が自動）、**付いたかを1つずつワールドで確かめる** |
| **部位の高さを、地面から別々に数えた** | 衝立のポスターを「地面+3から3段」、上の塀を「地面+4」と地面から数え、帯（土台1＋壁5＝地面+6）とは別に決めたので、衝立と帯の間に1段のすき間が空き、ポスターが足元に沈んだ | 高さは**名前の付いた基準（地面 G・床 F・帯 top）から**書く。**接する部位は相手の基準で書く**（衝立の上 ＝ `top - 1`、ポスターは植え込みの段 `G + 1` の上から）。施工の前に `run.py section` の断面と `run.py check` を必ず見る |
| **確認が自前の描画の1視点だけ** | 屋上が高すぎること、看板の向き、歩道の角の謎の箱に気づかなかった | 施工前に **お手本と同じ視点の絵** と、**部位ごとの横・正面の近い絵**を作り、部位表の数と1つずつ照らす。**入口の前に人（高さ2マスの目印）を置いて**、看板・塔・柵が人に比べて大きすぎないか見る |

**部位表**（設計を書く前に必ず作る。1行1部位）:
```
部位 | ブロックか飾りか | ブロック | 形（フル/ハーフ上下/塀/柵/板） | 幅×高さ×奥行（お手本を見て決めたマス数） | 1階の高さ・人との比べ | 位置（入口の中心・角からのずれ） | 高さの基準（何の上に載り、何の下に接するか） | 向き | 根拠（拡大画像のパス）
例: 屋上の柵 | ブロック | nether_brick_fence | 柵 | 縁に沿って×3段×1 | 1階の半分ちょっと・人の背丈くらい | 北と西の縁、塔の所は切る | 屋根（top）の上に載る | — | examples/kfc_kitahanada/parts/louver.png
例: 帯 | ブロック | 赤のハーフ | ハーフ | 全周×0.5×張り出し1 | 薄い線 | 1階の上端 | 壁の上（top） | — | examples/kfc_kitahanada/parts/band.png
例: 衝立 | ブロック | 深層岩レンガの塀＋ポスター | 塀 | 4×5×1 | 1階と同じ高さ | 扉の前、通り道の外 | 植え込みの段（G+1）の上に載り、上は帯（top）の真下に接する | 西 | examples/kfc_kitahanada/parts/entrance.png
```
報告では、建てた物の数と部位表の数を並べた表を出す（合っていない所は「合っていない」と書く）。
**部品（`parts.py`）が書き換わったら、辞書（recipes.md）の作り方と合っているか確かめてから使う。**
KFC で車止めの部品が「塀だけ」に書き換わっていたのに気づかず、辞書の「塀の上にランタン」と違う物を建てた。

**分からない所は、AA（文字の図）で質問してから作る。** 文章だけの質問は、写真の読み違いをそのまま問うことになり、
相手に意味が通じない（KFC で「扉はポスターの柱の左か右か」と聞いて通じなかった。実際は衝立の奥に通路と扉があった）。
- 平面（上から見た図）か立面（正面から見た図）を AA で描き、自分の理解を見せてから「ここで合っていますか」と聞く
- 目の位置と向き（👁 と ↓）、前後の順番（手前→奥）、マスの幅（░ 1つ = 1マス）を図に入れる
- 例（KFC の入口。正面から見て、手前から奥へ）:
```
   👁
   ↓
 塀 ポスター 塀      ← 深層岩レンガの塀で囲ったポスター（衝立）
     通路           ← 人1人分（1マス）
      扉            ← 正面の中央
```
```
 横から見た高さ（断面。左が歩道、右が建物。░ = ハーフ、█ = フルブロック）:
```
 歩道    通路の入口   通り道      扉の床
 ____    ░           ░░░░░       █        ← 歩道より ハーフ → 通り道もハーフ → 扉で1段
```
```
 歩道
 ───────────────────────────────────────
  植え込み（塀の縁＋間に砂利）  ↓通路  植え込み
 ═══════════════════════════  ░  ════════════
  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░   ← 人1人分（1マス）の通り道
 ─建物の壁─────────────────[扉]───────────
```

## 2. 作り方（手順）

### Step 0: 準備
- ワールドは **縮尺 1.4** で生成する（法則1）:
  `arnis --bbox "<南,西,北,東>" --file <OSM JSON> --gsi --plateau --scale 1.4 --output-dir <出力>`。
  生成直後のワールドのコピーは捨てない（控えの追加に使う）。`world_mapping.json` の `scale` が 1.4 か確認する
- サーバー: `minecraft-server/`（1.21.11、RCON `127.0.0.1:25575` / `arnis2026`）。ユーザーのターミナルで起動する
  （Claude の裏の実行は2時間で止まる）: `cd D:\develop\arnis-jp\minecraft-server; java -Xms2G -Xmx8G -jar server.jar nogui`
- 1.21.11 のゲームルール名は新形式（昼の固定は `gamerule advance_time false`）

- **視野角**: `tools/remodel/view.json` の `fov`（既定 **102**、ユーザーの Minecraft の設定）。ゲーム内と比べる絵はこの値で描く。
  **ユーザーが視野角を指定したら `view.json` を書き換えて覚える**（次の建物でもその値を使う）。
  写真の視点に合わせるカメラだけは `CAMERAS` に `vfov` を書く（写真のレンズに合わせる）

### Step 1: 建物と敷地を決める（ローカルデータだけ）
1. arnis の OSM JSON（`%LOCALAPPDATA%/arnis/osm_cache/` や `doc/kitahanada/osm_data.json`）で、
   店名の POI（`amenity`/`brand`/`name`）を探し、それを含む `building=*` の way ID を取る。
   日本語が文字化けするので Python で、`PYTHONIOENCODING=utf-8` を付けて実行する:
   ```python
   from parcel import OsmGeometry, ROOT, cells_in
   geo = OsmGeometry(ROOT / "doc/kitahanada/osm_data.json")
   for n in geo.nodes.values():                      # 店の POI を探す
       t = n.get("tags") or {}
       if "KFC" in str(t) or "ケンタッキー" in str(t):
           x, z = geo.to_mc(n["lat"], n["lon"]); print(n["id"], round(x), round(z), t.get("name"))
   for wid, w in geo.ways.items():                   # その点を含む建物
       if "building" in (w.get("tags") or {}) and (round(x), round(z)) in cells_in(geo.polygon(wid)):
           print("WAY =", wid, w["tags"])
   ```
2. 敷地 = その建物を含む `landuse` ∪ 建物のまわり5マス。**歩道・道路の手前で切る**。隣の構造物は `EXCLUDE` に
3. Web で敷地を探さない。ワールドを作り直すと座標が変わるので、毎回 OSM から変換する（コードが自動でやる）

### Step 2: 写真を読む（モデルの仕事。この表を埋めてからコードに入る）
**写真をそのまま目で見て決める。マス目を引いて画素を数えたり、m に換算したりしない**（法則1）。
細部が小さくて見えない時だけ、その部位を拡大して見る（形・厚さ・透け方を確かめるため。寸法を測るためではない）。

```
■ 1階の高さ: 店舗はおよそ 5 マス（これを基準にする）
■ 型（法則3の表から）: ______ → STACK = [...]
■ 屋根（法則4）: hip / gable(棟の向き __) / flat
■ 部位表（法則1.5）: 部位ごとに、形・ブロック・大きさ（1階の高さとの比、人との比べ）・位置・向き
   例: 塔 = 1階より少し低い・幅は入口2つ分くらい・入口の真上／看板 = 人の背丈より少し大きいくらいの正方形
■ 窓のある面: __（写っていない面は入れない）、柱の間隔 ___マス
■ 差し色の区画: ______（位置と大きさ）
■ 看板: 名前 / 大きさ（人と比べて）/ 色 / 位置と向き（店の顔なら地図アート）
■ 入口: どの面、凹み（ポーチ）か、段があるか（あれば PLINTH = 1）、柱・床の色
■ 外まわり（写っている物だけ）: ______
```

**Step 2 の最後に「分からない所の一覧」を作る。** 1つでもあれば、AA を付けてユーザーに聞き、答えをもらってから Step 3 に進む（0. 聞いてから作る）。

### Step 3: 設計ファイルを書く
サンプル `designs/kfc_kitahanada.py`（KFC 堺北花田。お手本と部位の拡大は `examples/kfc_kitahanada/`）を `designs/<建物名>.py` にコピーし、Step 2 の表の値に置き換える。
- 書き換える所: `WAY`/`LANDUSE`/`EXCLUDE`、`site_cells` の切り取り範囲、`STACK`、`ROOF`、`WINDOW_FACES`、
  `PILLAR_EVERY`、`DOOR_FACE`、`PLINTH`（土台の段数）、`PAL`（既定と違う素材だけ）、`footprint`（凹みを屋根で覆うか）、
  `signs`/`SIGN_BACKING`/`sign_images`、`CAMERAS`（写真の撮影位置）、`sections`（施工の前に見る断面）、`extras`（外まわり）
- **高さは `G`（地面）・`F`（床）・`top`（帯の段）から書く。接する部位は相手の基準で**（衝立の上 ＝ `top - 1`。地面から数えた数を並べない）
- **座標の計算は書かない**。部品（`parts.py`）に任せる。書くのは「どこに・何を」だけ

### Step 4: プレビューで写真と比べる
```
cd tools/remodel
python run.py <建物名> preview v1     # 置かずに描く → out/v1_street.png, out/v1_top.png（最後に自動チェックも出る）
python run.py <建物名> section        # 設計の sections(geo) の断面を AA で出す（入口・衝立・通路・仕掛け）
python run.py <建物名> check          # すき間・沈んだ看板・見える回路を探す
```
**断面の AA は、お手本と1段ずつ見比べる**（帯の下にすき間が無いか、看板が足元に沈んでいないか、床がハーフずつ上がるか）。
設計ファイルに `sections(geo)`（名前, 軸, 値）を書いておく。入口の中心・衝立の端・通路・自動扉の仕掛けは必ず入れる。
**`check` の警告は全部なくしてから施工する**（`build` は警告があると止まる。意図どおりの時だけ、ユーザーに確かめてから `build force`）。
写真と描画を上下に並べた1枚を作り、法則の順（大きさ → 数 → 差し色 → 奥行き）に違いを探す。
**1回に直すのは1か所**。直したら必ずもう一度描く。**プレビューと修正は最大3回まで**で、3回で施工に進む
（それ以上は法則の側を疑う。残りはゲーム内で見てもらって直す）。
カメラが構造物の中に入ったら、真上の図で空いている所に置き直す。
**入口の正面からの絵も必ず描く**（`CAMERAS` に `front`: 入口の正面 10 マスほど離れて目の高さ 1.6、`vfov` は書かない＝`view.json` の視野角）。
人の目の高さの絵で、看板・衝立・帯が**人の体と比べて**お手本と同じ高さに見えるかを、自分で確かめてから施工する。
写真の斜めの視点だけでは入口の違いに気づかない。比べる見本がゲーム内のスクショなら、同じ視野角・同じくらいの距離で描く
（近すぎ・視野角が狭すぎると建物の一部しか写らず比べられない）。

### Step 5: 施工
```
python run.py <建物名> build "メモ"   # チェック → 解体 → 控え → 施工 → 仕掛け → 飾り（付いたか確かめる）→ 看板の地図アート
python run.py <建物名> reset          # 更地に戻す（額縁も消す）
```

施工の最初に**解体**が自動で走る（`run.py` の `demolish`）。元の建物の土台からつながっているブロック
（敷地の外にはみ出した屋根・柵など）を、土台から6マス以内・ほかの建物に入らない範囲で全部たどって消す。
消した場所も控えに入るので `reset` で戻せる。

### Step 6: ゲーム内で確認
実際に**入口から歩いて入れるか**も確かめてもらう。
自前の描画は旗・額縁・光を描けない。テレポート先の座標をユーザーに伝え、見てもらう。
浮いているブロック、看板の表示、窓が隠れていないかを確認してもらい、1か所ずつ直す。

## 3. 躓きポイント（実際に踏んだもの）

| 症状 | 原因 | 対策 |
|---|---|---|
| 全体が低くて模型っぽい | 縮尺 1.0 のワールド、1階が低い | ワールドを縮尺 1.4 で作り、店舗の1階はおよそ5マス（法則1） |
| 看板・塔・柵が人の何倍も大きい | 画素を測って換算し、部位にまで 1.4 を掛けた | 画素を測らない。1階の高さとの比と、人の体と比べて目で決める（法則1） |
| 建物だけ大きくしたら隣・道路とぶつかる | 建物の平面だけ拡大した | ワールドごと `--scale 1.4` で作る（法則1） |
| 高架の下が低い | 縮尺 1.0 のワールド | 定数をいじらず縮尺 1.4 で生成（桁下も 1.4 倍になる） |
| ワールドを作り直したら座標がずれた | 設計ファイルに座標を直書き | 縮尺を変えたら座標も ×縮尺。なるべく建物のポリゴンからの相対で書く |
| 元の建物の屋根や柵が敷地の外に残る | 敷地の中しか消していなかった | 解体（つながっているブロックを追って消す）が `build` で自動で走る |
| 何度も作り直して大変 | 法則が曖昧で試行錯誤になる | 修正は最大3回。足りない所は法則・部品の側を直す |
| 文字の看板が建物並みに大きい | ブロックで文字を作ると5マス以上要る | 地図アートで実物大（法則7） |
| 赤（差し色）が多すぎる | 0.4m の帯が1マスに太る | 帯を壁の線だけにし、屋根の量で比率を戻す |
| 植え込みが1列しかない | 敷地を歩道から遠い所で切った | 敷地の端を歩道の手前まで広げる |
| 敷地を広げたら控えが無い | baseline は最初の敷地でしか撮っていない | `Construction.extend_baseline(生成直後のワールド)`。生成直後のワールドのコピーは捨てない |
| 施工したのにブロックが無い | 誰もいないとチャンクが読み込まれない | `builder.send()` が forceload する。`not loaded` は失敗として止まる |
| `Could not set the block` が大量 | 柵・鉄格子の「つながり方」だけ違う同じブロック | 失敗ではない（無視される） |
| 縦看板が浮いている | 地図アートの下に支えが無い | 根元も埋める |
| 屋上の柵が写真より低く・薄く見える | 壁の真上に fence で立てた（帯の陰で1段隠れる、棒で軽い）、高さも低めに読んだ | `parts.louver` で帯の外端に、軒との比で段数を決める（法則4） |
| 窓・ひさしが葉で隠れる | 生け垣・木が高すぎ | 生け垣は2段まで、木は窓の前に植えない |
| 写真の視点の絵が天井だらけ／構造物の中 | カメラ位置の決め打ち | 真上の図で確認、候補を3つ描いて選ぶ |
| 地面が想定と違う | 地形ありの生成で地面が上がる | 地面は毎回測る（`run.py` の `detect_ground`） |
| 敷地外エラーで止まる | 軒や看板が隣の構造物に掛かった | 安全装置が正しく働いている。設計か `EXCLUDE` を直す |
| 葉が消える | 自然の葉は時間で消える | `persistent=true`（既定で付いている） |
| 地図アートを描き直しても変わらない | サーバーが地図をキャッシュする | 施工ごとに新しい地図 id（`run.py` が自動でやる） |
| ピストン・扉が動かない（置き直しても伸びない） | 誰もログインしていないとサーバーが時間を止める（`pause-when-empty-seconds=60`）。コマンドでブロックは置けるが仕掛けは動かない | 扉の試験は誰かがログインしている時に行う（`list` で確かめる） |
| 看板が正しい面に付いていない | 以前は額縁が西向きにしか置けず、看板を別の面へ移していた | `signs` の5番目に向きを書く（`north`/`south`/`east`/`west`）。プレビューにも看板の絵が出るので、向きと位置を絵で確かめる |
| `Unknown block type 'minecraft:chain'` | 1.21.9 で鎖の名前が変わった | `iron_chain`（ブロック名はサーバーの版で確かめる） |
| ピストンの扉が閉じない・開かない | 置く順番（通電より先にピストンを置くと縮んだまま） | `auto_door` を使う。`Blocks.ordered` で最後に置く。防具立てで試す |

## 4. 性能の低いモデルで回すときのルール

- **モデルの仕事は3つだけ**: Step 2 の表を埋める、設計ファイルの値を置き換える、比較画像の違いを1つ言う
- **座標・形・安全確認はコード**（`parts.py`・`builder.py`）。設計ファイルに座標計算を書かない
- 表を埋めるまでコードを書かない。大きさに迷ったら、1階の高さとの比と、人（高さ1.8マス）と比べて目で決め直す
- 写っていないものは足さない（裏の面は窓なしの無地）
- **分からない所は推測で埋めず、AA を付けて聞く。答えをもらうまでその部位は作らない**
- 1回に直すのは1か所。直したらプレビューを見る。**最大3回**で施工に進む
- 施工前に `check_inside` が敷地外を止める。止まったら設計を直す（安全装置を外さない）

## 5. 道具（tools/remodel/）

| ファイル | 役割 |
|---|---|
| `run.py` | 入口: `python run.py <設計名> preview|section|check|build|reset` |
| `checks.py` | 施工の前の確かめ: `section`（断面の AA）、`inspect`（帯の下などの細長いすき間・足元に沈んだ看板・外から見えるレッドストーン） |
| `parts.py` | 部品ライブラリ: `build(spec, geo)`（床・壁・窓・ひさし・帯・屋根・看板の裏）、外まわりの部品、`entrance`（入れる入口。`steps="slab"` でハーフの段）、`planter_ring`・`eave_slab`・`lattice`・`box_on_roof`・`bollard`（部位の辞書の部品）、`sign_cells`（看板の向き）、`auto_door`（感圧板＋ピストンのガラス自動扉）、`furnish`（机・椅子・吊りランタン）、`louver`（屋上のルーバー）、`DEFAULT_PAL` |
| `scale.py` | （参考のみ）実寸 → マス数の換算。**部位の大きさを決めるのには使わない**（法則1: 目で見た比率と人の体で決める） |
| `block_catalog.py` | ブロックの色の対応表（全ブロックのテクスチャ・平均色・一番多い色と割合）と、写真の範囲 → 近いブロックを実物のテクスチャと並べる `match` |
| `view.json` | ユーザーの視野角（既定 102）。指定されたら書き換える |
| `map_art.py` | 地図アート（文字画像、減色、`world/data/` への書き出し） |
| `builder.py` | `Construction`: baseline の控え・`find_connected`/`add_demolition`（解体）・`extend_baseline`・`check_inside`・差分送信（forceload）・`place_frames`・`reset` |
| `parcel.py` | OSM のポリゴン → セル、外周、内側への距離 |
| `render.py` / `world_reader.py` / `block_colors.py` | 検証用の描画、リージョンファイルの読み込み、ブロックの平均色 |
| `designs/<建物>.py` | 建物ごとの仕様。git に入れるのはサンプルの `kfc_kitahanada.py` だけ（ほかの建物の設計は管理外） |

`builds/<建物>/baseline.json` は施工前の敷地の控えで、`reset` と解体に要るので消さない。

## 6. 正解例: 写真 → 仕様の対応（ガスト 堺北花田）

| 写真から読んだこと | 仕様 |
|---|---|
| 平屋のファミレス、軒 3.7m（自転車の人 1.6m で測った） | `STACK = ["glass"]*3 + ["frame+awning", "band"]`（柱5マス = 店舗1階の最低） |
| 寄棟の屋根、高さ 約1.8m | `ROOF = {"type": "hip", "rise": 2.5}`（頂部 約8マス） |
| 窓は西・北・南。東は写っていない | `WINDOW_FACES = {"w","n","s"}` |
| 南西が凹んだ入口ポーチ（屋根付き） | `footprint` で凹みを屋根に含める、`DOOR_FACE = "w"` |
| 赤い帯、赤白の縞のひさし | `band` = `red_concrete`、`awning` = 赤白のウール |
| 窓の柱間（写真で見て窓1枚がやや横長） | `PILLAR_EVERY = 4` |
| 屋根正面の「レストラン ガスト」、ポール看板、縦看板「から好し」 | 地図アート 8×1 / 3×3＋3×1 / 1×3（屋根の幅・人の背丈と比べて決めた）、裏は黒・赤・白のブロック |
| レンガの植え込みと生け垣、のぼり4本、駐輪ラック3、電柱、店先のタイル、点字ブロック | `extras` で `planter`・`nobori`・`bike_racks`・`pole`・`ground` |
経緯: v1（高さ ×1.5 過大・ブロックの巨大文字）→ v3（人の物差しで ×1.0、低すぎ）→ v6（柱5・頂部8、素材を種類で、地図アート）で正解。1階の高さ（柱5）はこの正解と KFC（柱4 で低すぎ）から決めた。
v8（KFC の失敗から）: ×1.4 を部位にまで機械的に掛けると大きくなりすぎる。1.4 はワールドの縮尺（ユーザーの黄金比）だけに使い、部位は目で見た比率と人の体で決める。
v7: 1.4 倍は「ブロックが粗いから」で、幅にも要る → ワールドごと `--scale 1.4` にし、座標・看板・間隔を 1.4 倍にした。
