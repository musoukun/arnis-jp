# skill_eval — スキルのテストを、記録から振り返る道具

Claude Code でスキルを動かしたあと、そのセッションの記録（Claude Code が自動で残す JSONL）を読んで、
次の5つを数字で出します。テストのたびに記録を残すので、スキルを直す前と後で比べられます。

| 見たいこと | 命令 | 分かること |
|---|---|---|
| 何にどれくらい時間がかかったか | `time` | 作業時間と人の返事待ちの分け、作業の種類ごとの回数と時間、遅かった道具、人の指示の一覧 |
| スキルのどの手順に時間がかかったか | `report` | スキルの手順（箱）ごとの時間と、前の手順に戻った所（やり直し）。HTML と draw.io の流れ図で見る |
| スキルが特定の例に偏っていないか | `scan` | 見出しごとに、特定の例（店名など）の言葉が出る行の割合。部品とスキルの文章の対応 |
| テストが書いたコードの質 | `code` | 部品をどれだけ使えたか、手で書いた所、座標などの直書き |
| 正解とどれだけ違うか | `compare` | プロファイルに書いた比較の命令を走らせ、違いの数を拾う |
| 全部まとめて残す | `report` | 上をまとめた記録を作業フォルダ `skill_eval/reports/` に Markdown と HTML（表と絵つき）で保存し、`skill_eval/reports/history.csv` に1行足す |

依存するライブラリはありません（Python 3.10 以上）。

## 使い方（スキルのテスト1回の流れ）

1. **新しいセッションでテストする。** プロジェクトの一番上（このリポジトリなら `D:\develop\arnis-jp`）で開きます。
   別のフォルダで開くと記録の置き場所が変わり、見つけられません。
2. **終わったら、テストのセッションの番号を一覧で確かめて、記録を残す。**
   ```text
   python .claude\skills\skill-eval\scripts\skill_eval.py image2mc-builder list
   python .claude\skills\skill-eval\scripts\skill_eval.py image2mc-builder report 6 --code kfc_test --compare kfc_test
   ```
   `list` は最近のセッションを、番号（1 が一番新しい）・開始時刻・長さ・最初の指示の書き出しつきで並べます。
   その番号を `report` に渡します。番号は新しいセッションができるとずれるので、`list` の直後に使います。
   `reports\<テストを始めた日時>_<プロファイル>_<セッション>.md` と同じ名前の `.html`、`reports\history.csv` ができます。
   HTML の一番上は「今回の結果と、スキルの直し方」の表です（取れる情報・今回の結果・分かること・スキルの直し方）。
   行は「どの手順に時間がかかったか」「前の手順に戻った所（やり直し）」「人が『それ違う』と言った所」「正解との一致」です。
   その下に「スキルの流れと時間」の図があります。箱がスキルの手順で、色が濃いほど時間が長く、赤の破線は前の手順に戻った所です。
   同じ図を draw.io で開いて直せるファイル（記録と同じ名前の `.drawio`）も、記録と一緒にできます。
   その下の部分（時間の順の流れ、どの作業が遅いか、正解との比較、前の回と比べる、細かい記録）はたたんであり、表の「くわしく」かナビで開きます。
   比べる絵は `--images "正解=絵1.png,テスト=絵2.png"` のように「ラベル=パス」で渡します（ラベルは省略可）。
   左右に2枚を並べた1枚の絵（真ん中に白い区切りがある物）を渡すと、左と右の2枚に自動で切り分けて組にします。
   `"正解|テスト=並べた絵.png"` のようにラベルを「|」で区切ると、左右の名前になります。
   テンプレートを直したあとは `python .claude\skills\skill-eval\scripts\skill_eval.py rerender <記録の HTML>` で、数字はそのままに描き直せます。
   同じテストをもう一度 `report` すると、記録のファイルも `history.csv` の行も上書きされます（重なりません）。
   日本語が化けるときは、先に PowerShell で `$env:PYTHONIOENCODING="utf-8"` を実行します。

1つずつ見たいときは、`report` の代わりに `time` / `cite` / `scan` / `code` / `compare` を使います（画面に出すだけで、保存しません）。

スキルごとのテストの手順と改善の回し方は、プロファイルの横の説明に書く（image2mc-builder なら `profiles/image2mc-builder.md`）。

## 命令

```text
python .claude\skills\skill-eval\scripts\skill_eval.py <プロファイル> list    [件数]
python .claude\skills\skill-eval\scripts\skill_eval.py <プロファイル> time    [セッション]
python .claude\skills\skill-eval\scripts\skill_eval.py <プロファイル> cite    [セッション]
python .claude\skills\skill-eval\scripts\skill_eval.py <プロファイル> scan
python .claude\skills\skill-eval\scripts\skill_eval.py <プロファイル> code    <ファイル>
python .claude\skills\skill-eval\scripts\skill_eval.py <プロファイル> compare [名前]
python .claude\skills\skill-eval\scripts\skill_eval.py <プロファイル> report  [セッション] [--code ファイル] [--compare 名前] [--images 絵1,絵2]
```

- `<プロファイル>`: `profiles/<名前>.json` の名前（例 `image2mc-builder`）
- `[セッション]`: 次のどれか。省略すると、一覧を出して止まります（今このコマンドを打っているセッション自体を読まないように）
  - `list` の番号（例 `6`）… いちばん簡単。番号は新しいセッションができるとずれるので、`list` の直後に使う
  - セッションID（例 `549d7bc8-e49e-4d8b-b213-ae59de2c8b50`）… ずれないので、あとで同じテストを記録し直すとき向け
  - `.jsonl` のパス
  - 最初の指示に含まれる文字 … 最初の指示にその文字を含む、一番新しいセッション
- セッションの記録は `%USERPROFILE%\.claude\projects\<プロジェクトのパスの : \ / を - にした名前>\<セッションID>.jsonl`

## 結果の読み方

### time（時間）
- **作業時間** ＝ 全体 −（人の返事待ち）。返事待ちは「アシスタントが発言を終えてから、人が次に打つまで」と、
  何も起きない 15 分以上の空白（放置）。
- **道具の実行** は、道具を呼んでから結果が返るまで。**考える・書く** は、その残り（モデルが考えて文やコードを書いている時間）。
- 1つの発言で道具を並べて呼んだときは、同時に動いていた時間をその数で割って数えます（重ねて足しません）。
- **作業の種類**はプロファイルの `categories` で決めます。上から順に当てはめ、どれにも当たらない物は「そのほか」。
- **考える・書く時間の内訳**: 道具を呼ぶ前にモデルが考えて書いていた時間と出力トークンを、その次にした作業に付けます。
  道具を呼ばずに発言を終えたときは「人への文章（報告・質問）」。長い物が遅さの原因です。
  出力トークンは発言ごとに1回だけ数えます（記録では1つの発言が「考え中・文・道具」の何行かに分かれ、どの行にも同じ数が入っているため）。
- **見た画像**: 読んだ画像の一覧。プロファイルの `visual_check`（正規表現）に合う画像は「自分で描いた絵で出来を確かめた回数」として別に数えます。
- **人の指示の回数**: 2 回目からは、質問への答えか、やり直しの指示。やり直しが多いほど「一発で」できていない。
  途中で止めた（`[Request interrupted by user]`）回数は別に数え、止めるまでは作業時間に入れます。
- **質問への答え**: 2 回目からの指示の中の「1.〜 / 2.〜」のような番号の数を、答えた項目の数として数えます。
- **長く考えた所**: 考える時間の内訳は「次にした作業」に付けただけなので、その作業が遅いとは限りません。
  何を考えていたかは、長く考えた所の上位 8 件（時刻・秒・直後にしたこと）で見ます。
- **人からの指摘**: 2 回目からの指示を文に分け、間違いを言っている文（「間違」「違う」「なんで」など。プロファイルの
  `correction_words` で変えられる）を数えます。答えとは別に数えるので、「一発でできたか」の目安になります。

### スキルの流れと時間（flow）
- プロファイルの `flow.steps` に、スキルの手順（箱）と、その手順に当たる作業の目印（`when`。書き方は `categories` と同じ）を書きます。
- 作業を時間の順に見ていき、目印に当たった手順に入ったとみなします。どの目印にも当たらない作業（`grep` で調べた等）は、その時いた手順の中の作業として数えます。
- 手順の時間は、その手順の中で「考えて文を書いていた時間」と「コマンドやファイルの読み書きの時間」の合計です。人の返事待ちは入れません。
- 前の手順に戻った回数は、スキルのどこで一発で進めなかったかの目安です。戻る前の手順に、足りなかった情報や決まりを書き足します。
- パスの目印は「/」で書きます（Windows の「\」は、比べる前に「/」にそろえます）。

### scan（偏り）
- 特定の例の言葉（プロファイルの `specific_words`）が多い見出しは、その例でしか使えない書き方になっている可能性があります。
- `library` を書くと、部品（関数）のうちスキルに書かれていない物と、スキルに書かれているのに無い物を出します。

### code（テストが書いたコード）
- 部品（`code.library`）の呼び出しが多く、手で書いた所（`code.manual_calls`）が少ないほど、部品で書けている。
- 直書きの数（既定 100 以上）は、座標などをそのまま書いた候補。絵を描く関数（PIL）の中の数と、
  `skip_keywords` に書いた引数（絵の大きさなど）は数えません。
- `count_patterns` で、好きな書き方の数を足せます（例: 地面から数えた高さ `G + 数`）。

### compare（正解との比較）
- プロファイルの `compare.command` を、リポジトリの一番上で走らせて、その出力を記録に入れます。`{name}` は命令の引数に置き換わります。
- プロファイルの `compare.metrics` の正規表現で、出力から数字を拾って `history.csv` に入れます（例: `一致: ([\d.]+)%`）。
- 比較の命令が「比べられない: 〜」と出したときは、数字の代わりにその理由を記録に出します（正解を取ったあとでワールドや建物の倍率が変わり、場所や大きさがずれている時など。数字を出すと実際より悪く見えるため）。そのときは、絵で見比べます。
- image2mc-builder では、ゲーム内で手直しした建物を `run.py <建物> capture` で正解として保存し、
  `run.py <設計> diff <正解>` で違いを数えています。

### history.csv（移り変わり）
1 テスト 1 行。列は、日時・作業時間・返事待ち・人の指示の回数・作業の種類ごとの回数（`n:〜`）・コードの数字・正解との一致（%）、など。Excel で開いて、スキルを直す前と後を並べて見ます。

## 別のスキルに使う

`profiles/image2mc-builder.json` をコピーして `profiles/<スキル名>.json` を作り、次を書き換えます。

| 項目 | 書くこと | 無くてもよいか |
|---|---|---|
| `root` | 評価するプロジェクトの一番上からの相対（ふつうは `.` のまま） | 無くてもよい |
| `skill_dir` | スキルのフォルダ（`root` から） | 必要 |
| `docs` | 見出しを数えるファイルと、数える見出しの深さ（`##` = 2） | 必要 |
| `flow` | スキルの手順（`steps`: `id`・`name`・`when`）。流れ図と、手順ごとの時間に使う | 無いと流れ図を描かない |
| `goals` | 目標。`{"項目": {"target": 0, "better": "lower", "label": "人からの指摘"}}`。項目は history.csv の列の名前（`corrections`・`match_pct` など）。一番上の表の「よい／直す所あり」に使う | 無くてもよい |
| `visual_check` | 自分で描いた絵（プレビューなど）のパスに合う正規表現。画像を見た回数のうち、出来を確かめた回数を分けて数える | 無くてもよい |
| `categories` | 作業の分け方。`tools`（道具の名前の一覧）・`tool_pattern`（道具の名前の正規表現）・`path`（読み書きしたファイル）・`command`（コマンド）・`input`（道具への入力全体）を組み合わせる。上から順に当てはめる | 無いと全部「そのほか」 |
| `cite.rules` | （`cite` の命令だけで使う。記録には入れない）見出しを、根拠の書き方の正規表現に変える規則。`heading` が見出しに合えば、`pattern` の `{1}` `{2}` を見出しの括弧の中身に置き換える。`skip: true` は数えない。どれにも合わない見出しは、見出しの名前（括弧の前）で数える | 無くてもよい |
| `specific_words` | 特定の例を表す言葉 | 無くてもよい |
| `library` | 部品のファイルとモジュール名、スキルに書かなくてよい内部の関数 | 無くてもよい |
| `code` | テストが書くコードの置き場所、部品のモジュール名、手で書いたとみなす呼び出し、直書きとみなす数の範囲 | `code` を使わないなら不要 |
| `compare` | 正解と比べる命令と、出力から拾う数字 | `compare` を使わないなら不要 |

## 限界

- 時間は記録の時刻から計算するので、道具の実行時間には、許可の確認を待った時間も入ります。
- 「考える・書く」は、記録の行と行のあいだの時間です。モデルの中で考えた時間と、文を書いた時間は分けられません。
- サブエージェントの中の作業は数えません（親のセッションだけ）。
- 記録（作業フォルダ `skill_eval/`。環境変数 `SKILL_EVAL_WORK` で場所を変えられる）は、手元の評価用です。git には入れません。
