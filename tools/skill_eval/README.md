# skill_eval — スキルのテストを、記録から振り返る道具

Claude Code でスキルを動かしたあと、そのセッションの記録（Claude Code が自動で残す JSONL）を読んで、
次の5つを数字で出します。テストのたびに記録を残すので、スキルを直す前と後で比べられます。

| 見たいこと | 命令 | 分かること |
|---|---|---|
| 何にどれくらい時間がかかったか | `time` | 作業時間と人の返事待ちの分け、作業の種類ごとの回数と時間、遅かった道具、人の指示の一覧 |
| スキルのどこが効いたか | `cite` | 見出しごとに、判断の根拠として使われた回数。一度も使われなかった見出し（削る候補）、スキルに無い判断（足す候補） |
| スキルが特定の例に偏っていないか | `scan` | 見出しごとに、特定の例（店名など）の言葉が出る行の割合。部品とスキルの文章の対応 |
| テストが書いたコードの質 | `code` | 部品をどれだけ使えたか、手で書いた所、座標などの直書き |
| 正解とどれだけ違うか | `compare` | プロファイルに書いた比較の命令を走らせ、違いの数を拾う |
| 全部まとめて残す | `report` | 上をまとめた記録を `reports/` に Markdown と HTML（表と絵つき）で保存し、`reports/history.csv` に1行足す |

依存するライブラリはありません（Python 3.10 以上）。

## 使い方（スキルのテスト1回の流れ）

1. **テスト用のプロンプトに、根拠を書く決まりを入れる**（`cite` を使うときだけ必要）。
   判断ごとに「根拠: 〜」の形で、使ったスキルの見出しを書かせます。スキルに無い判断は「根拠: なし（理由）」。
   ```text
   ■ 判断ごとに、使ったスキルの記述を「根拠: 〜」の形で書く（表の根拠の欄・コードのコメント・報告）。
     スキルに書いていない判断は「根拠: なし（自分で決めた理由）」と書く
   ```
   どんな書き方で見出しを指すか（例「根拠: 法則9」）は、プロファイルの `cite.rules` に合わせます。
2. **新しいセッションでテストする。** プロジェクトの一番上（このリポジトリなら `D:\develop\arnis-jp`）で開きます。
   別のフォルダで開くと記録の置き場所が変わり、見つけられません。
3. **終わったら、テストのセッションの番号を一覧で確かめて、記録を残す。**
   ```text
   python tools\skill_eval\skill_eval.py building-remodel list
   python tools\skill_eval\skill_eval.py building-remodel report 6 --code kfc_test --compare kfc_test
   ```
   `list` は最近のセッションを、番号（1 が一番新しい）・開始時刻・長さ・最初の指示の書き出しつきで並べます。
   その番号を `report` に渡します。番号は新しいセッションができるとずれるので、`list` の直後に使います。
   `reports\<テストを始めた日時>_<プロファイル>_<セッション>.md` と同じ名前の `.html`、`reports\history.csv` ができます。
   HTML をブラウザで開くと、次の順で見られます（見た目は `templates/report.html`。外部のライブラリは使わないので、ファイル1つで開けます）。
   1. **まとめ**: ゴールと現実（プロファイルの `goals` に対して達成か未達か）と、前の回との差
   2. **分析と直す候補**: 数字から読めることと、スキルや道具をどう直すと速く・正しくなるかの候補
   3. **処理の流れ**: 横が時間、1行が1つの作業の図。返事待ち・人の指示・指摘・途中で止めた所も描く。拡大でき、順番の一覧（表）も開ける
   4. **どこが遅いか**: 作業の種類ごとの、道具の時間と、その前に考えていた時間。長く考えた所と、遅かった道具
   5. **どこが読まれたか**: スキルの見出しごとの、根拠に使われた回数（使われなかった物だけにも絞れる）
   6. **正解との比較**: 違いの数と、比較の命令の出力。絵があれば「絵を比べる」で、左右・スライダー・違う所（重ねて差だけ明るく）の3つの見方
   7. **前の回と比べる**: 同じスキルのテストの一覧。2つ選ぶと、数字を左右に並べて差を出す
   8. **細かい記録**: Markdown の記録を全部
   比べる絵は `--images "正解=絵1.png,テスト=絵2.png"` のように「ラベル=パス」で渡します（ラベルは省略可）。
   同じテストをもう一度 `report` すると、記録のファイルも `history.csv` の行も上書きされます（重なりません）。
   日本語が化けるときは、先に PowerShell で `$env:PYTHONIOENCODING="utf-8"` を実行します。

1つずつ見たいときは、`report` の代わりに `time` / `cite` / `scan` / `code` / `compare` を使います（画面に出すだけで、保存しません）。

スキルごとのテストの手順と改善の回し方は、プロファイルの横の説明に書く（building-remodel なら `profiles/building-remodel.md`）。

## 命令

```text
python skill_eval.py <プロファイル> list    [件数]
python skill_eval.py <プロファイル> time    [セッション]
python skill_eval.py <プロファイル> cite    [セッション]
python skill_eval.py <プロファイル> scan
python skill_eval.py <プロファイル> code    <ファイル>
python skill_eval.py <プロファイル> compare [名前]
python skill_eval.py <プロファイル> report  [セッション] [--code ファイル] [--compare 名前] [--images 絵1,絵2]
```

- `<プロファイル>`: `profiles/<名前>.json` の名前（例 `building-remodel`）
- `[セッション]`: 次のどれか。省略すると、一覧を出して止まります（今このコマンドを打っているセッション自体を読まないように）
  - `list` の番号（例 `6`）… いちばん簡単。番号は新しいセッションができるとずれるので、`list` の直後に使う
  - セッションID（例 `549d7bc8-e49e-4d8b-b213-ae59de2c8b50`）… ずれないので、あとで同じテストを記録し直すとき向け
  - `.jsonl` のパス
  - 最初の指示に含まれる文字 … 最初の指示にその文字を含む、一番新しいセッション
- セッションの記録は `%USERPROFILE%\.claude\projects\<プロジェクトのパスの : \ / を - にした名前>\<セッションID>.jsonl`

## 結果の読み方

### time（時間）
- **作業時間** ＝ 全体 −（人の返事待ち）。返事待ちは「アシスタントが発言を終えてから、人が次に打つまで」と、
  何も起きない 15 分以上の空白（放置）。
- **道具の実行** は、道具を呼んでから結果が返るまで。**考える・書く** は、その残り（モデルが考えて文やコードを書いている時間）。
- 1つの発言で道具を並べて呼んだときは、同時に動いていた時間をその数で割って数えます（重ねて足しません）。
- **作業の種類**はプロファイルの `categories` で決めます。上から順に当てはめ、どれにも当たらない物は「そのほか」。
- **考える・書く時間の内訳**: 道具を呼ぶ前にモデルが考えて書いていた時間と出力トークンを、その次にした作業に付けます。
  道具を呼ばずに発言を終えたときは「人への文章（報告・質問）」。長い物が遅さの原因です。
  出力トークンは発言ごとに1回だけ数えます（記録では1つの発言が「考え中・文・道具」の何行かに分かれ、どの行にも同じ数が入っているため）。
- **見た画像**: 読んだ画像の一覧。プロファイルの `visual_check`（正規表現）に合う画像は「自分で描いた絵で出来を確かめた回数」として別に数えます。
- **人の指示の回数**: 2 回目からは、質問への答えか、やり直しの指示。やり直しが多いほど「一発で」できていない。
  途中で止めた（`[Request interrupted by user]`）回数は別に数え、止めるまでは作業時間に入れます。
- **質問への答え**: 2 回目からの指示の中の「1.〜 / 2.〜」のような番号の数を、答えた項目の数として数えます。
- **長く考えた所**: 考える時間の内訳は「次にした作業」に付けただけなので、その作業が遅いとは限りません。
  何を考えていたかは、長く考えた所の上位 8 件（時刻・秒・直後にしたこと）で見ます。
- **人からの指摘**: 2 回目からの指示を文に分け、間違いを言っている文（「間違」「違う」「なんで」など。プロファイルの
  `correction_words` で変えられる）を数えます。答えとは別に数えるので、「一発でできたか」の目安になります。

### cite（どこが効いたか）
- 数えるのは「根拠」を含む行だけです（スキルを読んだ・要約しただけの言及は数えません）。
- **一度も使われなかった見出し**は、そのテストでは効いていない記述。見出しの下に書いてあることの初めの部分も並べるので、何が効いていないかが分かります。建物（題材）によって使う見出しは違うので、
  **1回のテストで削らず、何回かのテストで続けて 0 なら削る候補**にします。
- **スキルに無い判断**（根拠なし）が何度も出るなら、その判断をスキルに書き足す候補です。

### scan（偏り）
- 特定の例の言葉（プロファイルの `specific_words`）が多い見出しは、その例でしか使えない書き方になっている可能性があります。
- `library` を書くと、部品（関数）のうちスキルに書かれていない物と、スキルに書かれているのに無い物を出します。

### code（テストが書いたコード）
- 部品（`code.library`）の呼び出しが多く、手で書いた所（`code.manual_calls`）が少ないほど、部品で書けている。
- 直書きの数（既定 100 以上）は、座標などをそのまま書いた候補。絵を描く関数（PIL）の中の数と、
  `skip_keywords` に書いた引数（絵の大きさなど）は数えません。
- `count_patterns` で、好きな書き方の数を足せます（例: 地面から数えた高さ `G + 数`）。

### compare（正解との比較）
- プロファイルの `compare.command` を、リポジトリの一番上で走らせて、その出力を記録に入れます。`{name}` は命令の引数に置き換わります。
- `compare.metrics` の正規表現で、出力から数字を拾って `history.csv` に入れます（例: `違い: (\d+) マス`）。
- building-remodel では、ゲーム内で手直しした建物を `run.py <建物> capture` で正解として保存し、
  `run.py <設計> diff <正解>` で違いを数えています。

### history.csv（移り変わり）
1 テスト 1 行。列は、日時・作業時間・返事待ち・人の指示の回数・作業の種類ごとの回数（`n:〜`）・根拠の数・
使われなかった見出しの数・コードの数字・正解との違い、など。Excel で開いて、スキルを直す前と後を並べて見ます。

## 別のスキルに使う

`profiles/building-remodel.json` をコピーして `profiles/<スキル名>.json` を作り、次を書き換えます。

| 項目 | 書くこと | 無くてもよいか |
|---|---|---|
| `root` | プロファイルから見たリポジトリの一番上（このフォルダの中なら `../../..` のまま） | 必要 |
| `skill_dir` | スキルのフォルダ（`root` から） | 必要 |
| `docs` | 見出しを数えるファイルと、数える見出しの深さ（`##` = 2） | 必要 |
| `goals` | ゴール。`{"項目": {"target": 0, "better": "lower", "label": "人からの指摘", "hint": "直し方"}}`。項目は history.csv の列の名前（`corrections`・`diff_cells`・`work_min` など）。まとめと分析に、達成か未達かが出る | 無くてもよい |
| `visual_check` | 自分で描いた絵（プレビューなど）のパスに合う正規表現。画像を見た回数のうち、出来を確かめた回数を分けて数える | 無くてもよい |
| `categories` | 作業の分け方。`tools`（道具の名前の一覧）・`tool_pattern`（道具の名前の正規表現）・`path`（読み書きしたファイル）・`command`（コマンド）・`input`（道具への入力全体）を組み合わせる。上から順に当てはめる | 無いと全部「そのほか」 |
| `cite.rules` | 見出しを、根拠の書き方の正規表現に変える規則。`heading` が見出しに合えば、`pattern` の `{1}` `{2}` を見出しの括弧の中身に置き換える。`skip: true` は数えない。どれにも合わない見出しは、見出しの名前（括弧の前）で数える | 無くてもよい |
| `specific_words` | 特定の例を表す言葉 | 無くてもよい |
| `library` | 部品のファイルとモジュール名、スキルに書かなくてよい内部の関数 | 無くてもよい |
| `code` | テストが書くコードの置き場所、部品のモジュール名、手で書いたとみなす呼び出し、直書きとみなす数の範囲 | `code` を使わないなら不要 |
| `compare` | 正解と比べる命令と、出力から拾う数字 | `compare` を使わないなら不要 |

## 限界

- 時間は記録の時刻から計算するので、道具の実行時間には、許可の確認を待った時間も入ります。
- 「考える・書く」は、記録の行と行のあいだの時間です。モデルの中で考えた時間と、文を書いた時間は分けられません。
- サブエージェントの中の作業は数えません（親のセッションだけ）。
- `cite` は、テストが「根拠: 〜」を書いてくれた分しか数えられません。書き方がそろうように、プロンプトで書き方を指定します。
- 記録（`reports/`）は、手元の評価用です。git には入れません。
