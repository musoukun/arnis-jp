# image2mc-builder スキルのテストと改善のしかた（skill_eval のプロファイル image2mc-builder 用）

このスキルで「一発で建つか」と「KFC だけでなく、どの建物にも使えるか」を、数字とユーザーの目で確かめる。

## 1. テストを別のセッションで行う

新しいセッションに、下のプロンプトを貼る（`<…>` を埋める）。
**汎用か確かめるには、KFC 以外の建物でも必ず1回行う**。KFC だけ通っても、KFC の答えを覚えているだけかもしれない。

```text
image2mc-builder スキルのテストです。写真1枚から「<建物名>」を Minecraft ワールドに建ててください。回答はすべて日本語で。
■ 入力: 写真 <写真のパス>（見た目の入力はこれだけ）、OSM の way <way ID か「店名から探す」>
■ 位置の指示: <人が最初から伝える位置の直し。無ければこの行を消す。KFC は下の「KFC で足す指示」>
■ 最初に .claude/skills/image2mc-builder/SKILL.md と recipes.md を全部読み、その手順どおりに進める
■ 見てはいけないもの: 作業フォルダ image2mc/designs/ にある既存の設計と、.claude/skills/image2mc-builder/examples/ の画像
  （KFC 以外の建物なら、正解のサンプル .claude/skills/image2mc-builder/examples/kfc_kitahanada/design_v2.py を完成例として読んでよい）
■ 分からない所は、スキルの「0. 聞いてから作る」どおりに私に質問する（質問の仕方もテストの対象）
■ 設計は作業フォルダの image2mc/designs/<設計名>/ のフォルダに書き（スキルの Step 3）、preview・section・check を見て、プレビューの絵を私に見せて OK をもらってから build する
■ 共有の道具（parts.py・run.py・checks.py・builder.py）とスキルのファイルは書き換えない。足りない部品は extras の中で作り「部品の不足」として報告する
■ check の警告で build が止まったら設計を直す（force は使わない）。git の commit・push はしない
■ 判断ごとに、使ったスキルの記述を「根拠: 〜」の形で書く（部位表の根拠の欄・設計ファイルのコメント・報告）。書き方は次のどれか:
  根拠: 法則9 ／ 根拠: Step 4 ／ 根拠: 0章・1.5・3章・4章・5章・6章 ／ 根拠: 辞書「植え込み（花壇）の縁」（recipes.md の見出し）
  スキルに書いていない判断は「根拠: なし（自分で決めた理由）」と書く
■ 最後に報告: 施工の結果、部位表、扉の中心の断面の AA、check の結果、質問と答え、スキルで迷った所、見る場所のテレポート命令
```

**KFC で足す指示**（2026-10-04 から）: 「位置の指示」の行に
`建物全体を OSM の位置より南へ6マスずらして（北側の面の前にドライブスルーの通り道を空けたい）` と書く。
テストを重ねるうちに建物が北へ寄り、北側の通り道が無くなった。写真からは分からない人の都合なので、スキルではなく依頼で伝える。
正解 v2 も南へ6マスずらしてある（`SHIFT_S = 6`）。これより前のテスト（3〜6）は、ずらす前の正解と比べた数。

## 2. テストのあとに数字を出す

評価の道具 `tools/skill_eval/`（使い方は `tools/skill_eval/README.md`）。リポジトリの一番上で、テストが終わったあとに1回:
```text
python tools\skill_eval\skill_eval.py image2mc-builder list
python tools\skill_eval\skill_eval.py image2mc-builder report <list の番号> --code <設計名>_test --compare <設計名>_test
```
時間・根拠（cite）・コード・正解との違いをまとめた記録が `tools/skill_eval/reports/` に残り、`history.csv` に1行足される。
1つずつ見るときは `report` の代わりに `time` / `cite` / `scan` / `code` / `compare`。
（日本語が化けるときは、先に PowerShell で `$env:PYTHONIOENCODING="utf-8"`）

| 見る数字 | 良い | 悪い（スキルか部品を直す） |
|---|---|---|
| 作業時間のうち「写真・画像を見る」「コードを読む」 | 短い | 長い ＝ スキルの手順が分かりにくい・迷っている |
| プレビュー・施工の回数 | プレビュー3回まで、施工1回 | 多い ＝ 一発で建っていない |
| 1回目のあとの人の指示 | 質問への答えだけ | 「ここ違う」のやり直しが多い ＝ ルールが足りない |
| 手で置いたブロック（c.put） | 少ない | 多い ＝ その建物に要る部品が無い（`parts.py` に足す候補） |
| 座標の直書き | 0 | ある ＝ ワールドを作り直すと壊れる |
| 高さを地面から数えた所 | 少ない（地面に置く物だけ） | 多い ＝ 接する部位が相手の基準で書かれていない |
| スキルの特定の建物の行 | 例として出るだけ | 決まりが KFC の部位の名前でしか書かれていない ＝ ほかの建物に当てはめられない |

KFC と別の建物で同じ数字を並べると、KFC だけ良い所が「KFC にしか効かないルール」と分かる。

**何が何に効いているか**は `cite` で見る。何回かのテストで続けて一度も引かれない見出しは削る候補、
「根拠: なし」で何度も出てくる判断は、スキルに足す候補。1回のテストだけで削らない（建物によって使う見出しが違う）。

## 4. 改善の回し方（KFC で回している手順）

1回の改善は、次の8つの手順で回す。速いモデル（Sonnet）で一発で建つことを目指す。

1. **版を残す**: スキルのフォルダ（`.claude/skills/image2mc-builder/`。道具・型・正解の設計を含む）を zip にして `tools/skill_eval/versions/` に置く
   （`image2mc-builder_<日時>_<何の前か>.zip`。git には入れない）。いつでも前の版に戻れるようにする
2. **テストする（Sonnet のサブエージェント）**: 渡すのは写真1枚・OSM の way 番号・スキルの3つのファイルだけ。
   答えになる設計（正解・前のテストの設計）・お手本の画像・既存のプレビューは見せない。設計名は `kfc_test<番号>`。
   サブエージェントは Agent を起動できないので、Step 3 の受け持ちの表（`plan.md`）ができた所で止まる。
   親（テストする側）が plan.md の依頼文で Sonnet の Agent を行の数だけ並列に起動し、全員が終わったら
   テストのサブエージェントに会話の続き（SendMessage）で「パーツがそろった。Step 4 から続けて」と伝える
   パーツの依頼文には、テストの依頼文と同じ「見てはいけないもの」（正解・前のテストの設計・お手本の画像）を足す
   （テスト7で、パーツ担当の1人が前のテストの設計のロゴを参考にした）
3. **質問には、人がフォームで答える範囲だけで答える**: スライダーと選択肢の値と、補足欄に書きそうな短い一言の1行だけ。
   答えを知っている側が設計図のような説明を足さない（足すと「書き写せるか」しか測れず、スキルの弱点が隠れる）
4. **施工の前で止め、プレビューを確かめてから施工する**: `run.py <設計> check` と、正解（v2）と同じ視点で並べた絵を作り、
   それから `build`。施工前の状態は控えに残るので `reset` で戻せる
5. **記録を残す（skill_eval）**: サブエージェントの記録（`tasks/<id>.output`）を写して
   `python tools\skill_eval\skill_eval.py image2mc-builder report <記録> --code <設計> --compare <設計> --images "正解=<v2の絵>,テスト=<テストの絵>"`。
   HTML の **まとめ（ゴールに届いたか・前の回との差）**・**分析と直す候補**・**処理の流れ**・**前の回と比べる**・**絵を比べる** を見る。
   比べる表は手で作らない（「前の回と比べる」で2つ選ぶ）
6. **本人に振り返らせる**: テストした Sonnet に、会話の続きとして結果（並べた絵と、正解との違い）を見せ、
   「なぜそうなったか」「何があれば作れたか」「効く順に3つ」を聞く
7. **直す**: skill_eval の「分析と直す候補」・本人の答え・絵の違いから、次の3種類に分けて直す
   - スキルの文章（決まりが無い・食い違っている・例外が広すぎる）
   - 道具（部品・型・命令が無いので、毎回自分で組んで失敗する）
   - 質問（聞くべきことを聞いていない・聞かなくてよいことを聞いている）
   直したら、正解の設計を新しい部品で書き換えて、正解との違いが 0 マスになることを確かめる（部品が正しいことの確かめ）
8. **次のテストへ**: 1 に戻る。テストの番号を1つ進め、同じ条件で比べる

### SKILL.md 1.5 の表（原因・起きたこと・決まり）

## 1.5 ミスを防ぐ決まり（KFC の失敗から。必ず守る）

KFC でお手本と比べて10か所違った。原因は10で、どれも「お手本を目で見る前に、別の物で決めていた」こと:
| 原因 | 起きたこと | 決まり |
|---|---|---|
| **道具の都合を形より優先** | ランタンを吊るために帯をフルブロックにした／地図アートが西向きしか置けないので看板を正面に置いた | 部品で作れない形は、形を変えずに**道具の側を直す**（部品の不足として先に報告） |
| **画素を測って換算を重ねた** | マス目で画素を数え → m に直し → ×1.4 → 最低マス数、と重ねて、看板・塔が人の何倍もの大きさになった | **画素を測らない。目で見た比率と人の体で決める**（法則1）。1.4 はワールドの縮尺（ユーザーの黄金比）で、部位に掛けない |
| **数をお手本で数えず、文章のルールや古い座標から決めた** | 塔を高さ8・屋上の柵を5段にした（お手本は塔4・柵3段）／看板と植え込みを古い設計の座標のまま使った | 部位ごとの数（幅・高さ・奥行き・段数・位置・向き）は**お手本を見て部位表に書く**。**古い設計の座標を使い回さない** |
| **指摘された所だけ直した** | 植え込みのハーフを直したのに、同じ「厚さを見る」原則を帯に当てなかった | 指摘を受けたら、その原則で**全部の部位を点検し直す** |
| **形だけ見て、人の動き（動線）を読まなかった** | 植え込みの切れ目と階段を「縁の飾りの段々」と読み、左右2つの通路から衝立の裏を通って扉へ入る作りを見落とした | 部位を見る前に、**歩道から扉まで人がどう歩くか**（車ならドライブスルーの通路）を平面の AA に描く。**段・階段・植え込みの切れ目は通路の印**。「なぜここに段があるのか」を必ず考える |
| **通路の高さを歩く順に考えなかった** | 衝立の裏の通り道を平らな地面のままにし、段は扉の前だけにした（実物は通り道をハーフで底上げし、通路の入口で1段上がる） | 入口・通路は、**横から見た高さの図（断面の AA）を描く**。歩道→通路→通り道→扉の各マスの床の高さをハーフ単位で書き、段をどこに置くかを決めてから作る |
| **軒を形の外周に機械的に回した** | 帯（軒）が壁の1マス外で止まり、前に出た衝立の上を覆わなかった | 衝立・看板・ひさしなど**前に出る物を足したら、上から見た図で軒の線と重ねる**。入口のまわりは軒を前に出して覆う（覆わない時は理由を書く） |
| **辞書に書いた作りが建った物に入っているか確かめなかった** | 辞書は「車止め＝黒い塀の上にランタン」なのに、部品が塀だけを置いていて明かりが付かなかった | 部位表で**ブロックか飾りか**を分ける。ランタン・トーチ・鎖・感圧板・旗などの飾りは、**ブロックを全部置いた後に最後に取り付け**（`Blocks.decor`、`run.py` が自動）、**付いたかを1つずつワールドで確かめる** |
| **部位の高さを、地面から別々に数えた** | 衝立のポスターを「地面+3から3段」、上の塀を「地面+4」と地面から数え、帯（土台1＋壁5＝地面+6）とは別に決めたので、衝立と帯の間に1段のすき間が空き、ポスターが足元に沈んだ | 高さは**名前の付いた基準（地面 G・床 F・帯 top）から**書く。**接する部位は相手の基準で書く**（衝立の上 ＝ `top - 1`、ポスターは植え込みの段 `G + 1` の上から）。施工の前に `run.py section` の断面と `run.py check` を必ず見る |
| **確認が自前の描画の1視点だけ** | 屋上が高すぎること、看板の向き、歩道の角の謎の箱に気づかなかった | 施工前に **お手本と同じ視点の絵** と、**部位ごとの横・正面の近い絵**を作り、部位表の数と1つずつ照らす。**入口の前に人（高さ2マスの目印）を置いて**、看板・塔・柵が人に比べて大きすぎないか見る |
